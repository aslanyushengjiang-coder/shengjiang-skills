# 客户库：服务谁，承诺过什么，下一步做什么

管理客户、合作销售伙伴、商机、交易和服务事实。先读本说明与本库 `_资料索引.md`，按授权范围定位原件；不在通用索引展开身份证号、健康详情或完整聊天内容。

## 建议子库

按实际业务启用下列分类。已有目录只做映射；有资料或明确任务再创建子目录，空缺登记在索引。每个客户、商机、订单有一个主档案，关联其他事实，不在多个分类复制客户全套资料。

| 建议子库 | 放什么 | 归属边界与使用条件 |
| --- | --- | --- |
| 01.家庭与个人客户 | 家庭与联系人关系、孩子适龄信息、出行偏好、参与历史、服务需要、触达许可 | 区分付款人、监护人和参与人；过敏、健康和证件信息只在履约必要且获授权时引用受控原件，不进入公用摘要 |
| 02.学校企业与团体客户 | 学校、年级、班级、家委、企业和其他团体档案，联系人角色、采购流程、合作历史 | 客户实际提出的目标、人数与预算保留证据；某次需求进商机，已实施项目引用产品库团期档案 |
| 03.同业渠道与合作伙伴 | 组团社、分销商、转介绍合作方、渠道协议、佣金/分成条款、渠道归因和合作记录 | 采购资源方归产品库供应资源。佣金约定与支付记录分别登记；给某个同业客户的报价留商机或订单 |
| 04.需求商机与沟通 | 咨询记录、已导出聊天、需求问卷、预算和时间、方案/报价版本、招标文件及本次投标应答、跟进事项、成交/流失原因 | 需求事实、销售判断和 AI 推测分开；本次方案引用产品与资源；不能仅凭情绪标签判定客户意向或购买力 |
| 05.订单合同与收退款 | 报名订单、客户合同、付款依据、收款/退款、发票、优惠、次卡/会员权益、客户或渠道结算 | 已报价、已确认、已签约、已收款分开；业务系统或财务凭证为依据，聊天提及付款不等于实收。供应商付款归团期成本与供应结算 |
| 06.出行服务与关怀 | 本次参与名单、分组/分房/分餐/分车所需个人信息、行前沟通、签到、服务要求、孩子个人反馈、照片交付和回访记录 | 团期整体安排由产品库主档管理；这里保留客户级事实，按需引用最少信息。禁止把健康详情带入营销内容 |
| 07.评价售后与转介绍 | 评价、投诉原文、处理承诺、退款处理关联、服务补救、转介绍授权与结果 | 记录问题、责任人、承诺期限、处理证据和当前状态；已起草回复不等于已发送或已解决 |
| 08.客群洞察与运营 | 有来源的客户分组、购买问题、需求统计、活动效果、复购和会员运营记录 | 原始记录保留在客户/订单主档，这里做必要的脱敏汇总；记录样本范围与统计时间。不能用主观印象补造客户画像 |

## 对象之间怎样关联

家庭/机构/渠道 → 本次商机 → 订单 → 产品库的具体团期。参与人可以与付款人不同，一个团期可以服务多个家庭或订单，一个客户也可以参加多个团期。沿用已有编号和原系统链接，不用手机号或身份证号充当公开索引标识。

商机记录至少能找到需求、来源、责任人、当前阶段、下一步及期限；订单至少能找到产品/团期、约定版本、交易状态和依据。没有下一步日期就保留待补，不能自行虚构承诺。

## 常见调用

定制方案先读具体需求与已承诺条件，再读产品库资源、价格与交付能力，以及技能库方案报价流程。分房分车只读取这次已确认订单和必要名单字段，交付后检查人数、同住条件与冲突。复购活动从真实历史订单和触达许可筛选名单，再引用当前可售产品；发消息仍需明确发送授权。

记录中同时出现“客户原话”“员工判断”“AI建议”时分别标注。成交、退款、投诉解决等状态须有对应系统、凭证或明确确认。新增判断先保留为待验证，不反向改写原始聊天。

## 结果反馈

一次服务结果先回写客户/订单原记录，涉及产品的问题再向产品反馈建立引用；被多次验证的处理方法可以提炼到技能库，删除个人信息并保留适用条件和验证证据。客户原文、统计结论和操作方法各有主归属。
