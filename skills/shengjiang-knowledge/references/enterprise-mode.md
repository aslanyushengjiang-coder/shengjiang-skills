# 企业三库模式

用户要求企业知识库、公司资料整理，或明确产品库、客户库、技能库时读取。旅游、亲子游、研学机构使用下面的业务分类；其他行业沿用三库职责，按真实资料命名内容。

## 先了解公司和资料

从当前对话与已读资料提取已有答案，一次询问缺失的关键问题：

1. 公司有哪些角色、服务谁、最常做哪些任务？允许组团、地接、学校研学、营地等多种角色并存。
2. 资料在哪、已有目录怎样分、哪些业务系统管理有效的产品/客户/订单/库存？谁负责确认和更新？
3. 知识库保存在哪里、优先完成什么结果？哪些客户资料限制使用，哪些资料不纳入？

用户明确要求“开始前先问”时，先询问并等回答，再扫描和写入。已经回答的内容不重复询问。来源路径和目标路径必须真实明确；截图里的「这里换成你的文件夹」是占位符，不能当成路径。

## 三库怎么区分

| 业务库 | 回答什么问题 | 收录什么 |
| --- | --- | --- |
| 产品库 | 能卖什么、能交付什么、如何改进？ | 市场与产品规划、供应资源、线路课程、成本价格、团期交付、品牌资料、内容素材、产品迭代 |
| 客户库 | 服务谁、承诺过什么、交易与服务到哪里？ | 家庭个人、学校团体、同业渠道、商机沟通、订单收退款、出行服务、售后转介绍、客群运营 |
| 技能库 | 工作如何执行、如何验收和改进？ | 研发采购、内容获客、咨询报价、计调准备、现场安全、教学评价、售后复盘、岗位与工具 |

## 易混淆的归属

按正文和用途分类，不能按 PDF、表格、图片等格式分类：

- 某条线路的通用报价在产品库；给某个客户的报价及谈单结果在客户库；如何核算报价的步骤在技能库。
- 产品是可复用的线路/课程，团期是某次实际交付。团期主档在产品库，关联产品版本、资源、订单和适用 SOP；客户个人名单与健康资料留客户库受控位置，不复制到公用产品文档。
- 供应商档案、采购条款归产品库；销售渠道归客户库。同一机构兼具两种角色时用引用关联，主体档案只有一份。
- 采购合同归资源，销售合同归客户订单，团期成本和供应结算归团期，通用核算方法归技能库；现有财务账本只引用。公司人事、法务等专业档案保持原系统，仅纳入当前业务所需引用。
- 某产品的具体教案、研学手册归产品库，设计教案与教学组织的方法归技能库；某客户的投标文件归本次商机，机构通用资质归产品库，投标流程归技能库。
- 已发布的某次活动公众号文章在产品库，记录活动与发布状态；公众号制作流程和通用排版模板在技能库。
- 某个客户的聊天原文在客户库；从聊天中提炼的通用接待流程在技能库，保留来源关联并去除个人信息，标明“待验证流程”。
- 同一原件涉及多个库时，只登记一个主归属，其他库用引用关联。混合表格按工作表或具体页码建立引用；不能为分类改动原表。
- 技能库首先是团队的做事方法，不要求每份 SOP 都变成可安装的 AI Skill。已有可执行 Skill 可以登记安装位置与适用任务，只有用户要求封装时才生成。
- 无法判断的文件保留原位置，在交付清单登记“待分类”；不新建第四个业务库。

## 建立入口，保留原件

三库是业务导航。根入口和 system 负责协作规则，不构成其他业务库。

新库或缺入口的资料目录先预览：

```bash
python3 scripts/init_knowledge_base.py --root "<知识库绝对路径>" --name "<公司名称>" --profile enterprise
```

已授权搭建且路径明确，检查预览后加 `--apply`，无需逐文件重新批准。只要求方案时停在预览。脚本仅创建缺失入口和空索引，不读取、分类或迁移资料；创建目录完成只能报告“结构已建立”。所有脚本路径相对本 Skill 安装目录，从其他目录执行时使用绝对路径。

已有成熟库先把三个业务职责映射到现有目录，更新现有导航；不得套用初始化脚本制造第二套库。脚本不覆盖已有文件，重复执行不能代替读取、维护已有入口；明确补充缺失文件后才使用初始化。

原件保持位置、文件名和内容。新库通过原路径引用资料，只新增索引、接入卡和必要加工件。来源在库外时使用可打开的绝对路径链接，记录来源范围；不复制整批原文，不默认扫描全盘。

区分接入的原始证据与用户授权持续维护的业务主档：历史合同、原始报价和聊天保持原样；产品主档、订单状态和 SOP 可在相应授权范围更新并保留依据。外部系统的事实只能通过其授权入口更新，未更新成功的事项留待处理。业务纠正回所属主档或流程，跨任务协作习惯才进入系统规则。

## 分批接入

1. 只读运行 `scripts/scan_materials.py --source "<资料绝对路径>" --format markdown`。清单只是目录盘点。
2. 分批实际读取文件正文和附件。代表样本用于确定分类；用户要求整理整批资料时逐项覆盖，登记未读、待转换、云端未下载和权限不足项。图片需核验内容，音视频依当前环境允许的字幕或转写能力处理。
3. 在主归属库的 `_资料索引.md` 记录子库分类、标题、类型、原始路径、来源/负责人、资料日期、读取状态、有效状态、关联对象和缺口。沿用已有产品/团期/客户/订单标识。读取状态与业务有效状态分开：已读取不代表当前报价有效。
4. 报价至少核验适用日期、团期、人数/年龄条件、包含与不含项目；缺失时如实记录。旧报价和同名版本保留冲突，不凭修改时间选“最新”。
5. 客户信息只在授权范围读取和使用；名单与已导出的聊天可以整理，原始聊天数据库、账号凭据、Cookie 和密码文件跳过。不自动联系客户、不发送消息。普通本地文件夹不提供人员权限隔离，用户限制访问时保留到指定受控位置并引用，不宣称已配置权限。
6. SOP 保留适用场景、输入、步骤、负责人、交付物和检查标准；资料里没写的标记缺口，Agent 建议不能冒充团队已执行的流程。
7. 更新最近索引、根导航中的三库映射、公司背景和变更日志，然后运行健康检查。已授权保存结果时加 `--save-state`。

## 交付和验收

更新 `system/三库交付清单.md`，已有等价报告就复用它。清楚记录：

- 产品库、客户库、技能库各放了什么，索引在哪，有哪些实际可打开的原件。
- 各库已登记、已读、待转换/未读数量；各项计数采用文件还是记录口径，重复引用不重复算原件。
- 还缺哪些资料、影响哪个任务、需要谁补充；“本轮范围未发现”不写成“公司没有”。
- 原件保留情况、扫描范围、未处理项和版本冲突。
- 从本批真实材料各选一个产品、客户、流程问题，沿索引找到原件并回答；某库没有可读资料就说明该库待补，不能编造演示答案。
- 选择本机构真实需要的一个跨库任务，验证需求 → 产品/资源 → SOP → 结果保存 → 检查与更新；检查缺少输入、价格/团期变更、执行中断时怎样处理。未进行真实执行的部分如实标记。

三库空模板不等于资料接入完成；健康检查通过不等于正文已读完或 WorkBuddy 已真实运行。最终回复给用户三库入口和缺口清单，清楚区分已建立结构、已接入资料、尚待处理。
