# shengjiang-knowledge 架构说明

> 搭建或升级知识库时读取。这里解释各层为什么存在，不要求用户照抄固定目录名。

## 核心判断

知识库的价值不是“存了多少文件”，而是 Agent 能否在需要时获得五类上下文：

| 上下文 | 默认载体 | 解决的问题 |
| --- | --- | --- |
| 我是谁 | `system/USER.md` | 不再每次重新介绍用户、业务和目标 |
| 怎么协作 | `system/SOUL.md` | 固定语气、关系和协作偏好 |
| 遇到事情怎么做 | `system/PROCEDURES.md` | 把反复纠正变成程序性规则 |
| 现在最重要什么 | `_本周.md` | 防止 AI 只看历史、不看当前重点 |
| 资料和事实在哪里 | `INDEX.md` + 原始文件 | 按需检索，并能追溯依据 |

## 最小结构与成熟结构

最小知识库只需要跑通入口、记忆、规则、当前工作、资料和输出。业务变多后再增加业务区、项目档案、区域入口和 Skill 注册表。

不要因为看过成熟样板，就给新用户一次性创建十几个空目录。判断标准是：这个目录今天是否有真实内容、真实流程或近期复用价值。

## 信息流

```text
未判断的新输入 → 00.收件箱
可长期复用的资料 → 01.资料库或业务区
正在制作的成果 → 02.输出区
一次真实项目的全过程 → 项目档案（成熟后增加）
重复出现的判断和动作 → PROCEDURES / Skill
用户纠正 → MEMORY_LOG → 重复达到阈值后升级规则
```

## 事实源原则

1. 本地原始文件是事实源，导航和摘要只负责指路。
2. 外部协作平台默认是镜像或协作层，除非用户明确指定它为权威源。
3. 多个版本并存时，必须有日期、状态或索引规则说明当前使用哪个。
4. 无法判断权威版本时保留冲突并询问，不替用户猜。

## Agent 入口原则

- 入口要短，只加载每次都需要的规则和导航。
- 长工具手册、完整项目清单和历史资料按需读取。
- 同一长期规则只维护一个真源，其他 Agent 使用薄入口或 bridge。
- 修改入口后必须检查引用路径和镜像一致性。

## 为什么要有日志和自检

没有日志，知识库会变化但无法解释；没有自检，入口、索引和真实目录会慢慢漂移。

最小反馈层包括：

- `system/log.md`：只增不改，记录结构和规则变化；
- `system/MEMORY_LOG.md`：记录用户纠正；
- `system/state/`：保存巡检结果；
- 周期性巡检：断链、入口、版本、积压和敏感文件。
