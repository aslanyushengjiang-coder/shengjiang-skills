# shengjiang-workbench：个人 AI 工作台生成与迭代

## 目标

把“送一份固定提示词”升级为可重复运行的搭建流程：

```text
了解用户 → 规划模块 → 用户确认 → 生成可运行初版
→ 检查真实交互 → 按截图或反馈修改 → 选择长期升级
```

工作台不是静态效果图。初版至少要能打开、能新增和删除内容、能刷新后保留数据、能导入导出备份。

## 路由

| 用户意图 | 模式 |
| --- | --- |
| 不知道自己需要什么 | 需求诊断 |
| 已说清需求，希望直接搭建 | 规划后生成 |
| 给了现有页面、截图或代码 | 迭代已有工作台 |
| 要手机电脑同步、登录或 AI 助手 | 长期升级 |
| 怀疑页面只是空壳或功能坏了 | 健康检查 |

## 边界

### 默认直接执行

- 读取用户明确提供的需求、截图、工作流和现有项目。
- 在信息足够时生成需求摘要、模块方案和文件预览。
- 运行 `scripts/build_workbench.py` 的预览模式。
- 运行 `scripts/audit_workbench.py` 做只读检查。

### 写入前确认

- 用户尚未明确要求“创建、搭建、修改”时，先展示模块方案。
- 目标目录已存在文件时，列出影响范围；禁止静默覆盖。
- 删除模块或迁移现有数据前，说明备份和兼容性影响。

### 不得冒充现成功能

- 本地版默认使用浏览器 `localStorage`，不是云同步。
- 静态页面不能安全地直接保存 API Key。
- 登录、跨设备同步、多人协作、数据库和真实 AI 助手需要后端或第三方服务。
- 未实际打开和操作验证的页面，不得声称“已经可用”。

## 第一步：建立需求画像

如果用户已经给出足够信息，不要重复提问；从现有对话提取并让用户确认。

信息不足时，按 `references/intake.md` 进行一轮简短访谈。优先获得：

1. 工作台服务的角色和核心目标；
2. 每天或每周反复发生的工作；
3. 输入资料、处理动作和最终输出；
4. 当前最痛的三个问题；
5. 使用设备和是否需要跨设备；
6. 必须有、可以晚点有、明确不要的能力。

不要一次抛出十几个问题。每轮只问会改变模块设计的关键问题。

如果用户明确要视频对标的“三份文档”，使用：

- `assets/01-个人信息填写表.md`
- `assets/02-一键生成提示词.md`
- `assets/03-长期维护与云端同步升级指令.md`

来源还原边界见 `references/reconstruction-notes.md`。第三份是根据视频逐字稿重构的增强版，不得冒充博主未公开的原始 Word 文件。

## 第二步：规划模块

读取 `references/module-catalog.md`，把需求映射成 4–8 个模块。每个模块必须说明：

| 字段 | 含义 |
| --- | --- |
| 名称 | 用户看得懂的菜单名 |
| 解决的问题 | 为什么需要它 |
| 输入 | 用户或系统放入什么 |
| 动作 | 在模块里完成什么 |
| 输出 | 最后得到什么 |
| 优先级 | 首版 / 二期 / 可选 |

默认建议保留三个底座：

- **今日**：当前任务、优先级和完成状态；
- **收集箱**：承接零散输入，等待整理；
- **设置与数据**：导入、导出、备份和使用说明。

不要因为目录里有模块模板，就全部推荐给用户。

## 第三步：确认首版

生成前给出简洁确认单：

```markdown
工作台：{名称}
核心目标：{一句话}
首版模块：{4–8 个}
暂不包含：{云同步 / 登录 / AI API / 其他}
数据方式：本机浏览器保存，可导入导出 JSON
生成位置：{绝对路径}
```

用户已经明确说“直接做”“搭建”时，这份确认单作为执行说明，不必再次阻塞等待。

## 第四步：生成可运行初版

把确认后的需求写成 UTF-8 JSON，字段格式见 `assets/profile.example.json`。

先预览：

```bash
python3 scripts/build_workbench.py \
  --profile "<需求画像.json>" \
  --output "<绝对输出目录>"
```

确认目标无误后生成：

```bash
python3 scripts/build_workbench.py \
  --profile "<需求画像.json>" \
  --output "<绝对输出目录>" \
  --apply
```

也可以用内置场景快速打样：

```bash
python3 scripts/build_workbench.py \
  --preset creator \
  --output "<绝对输出目录>" \
  --apply
```

支持的预设：`personal`、`creator`、`study`、`product`。

其中 `study` 是视频对标所展示的学习工作台底座，默认包含：

- 今日；
- 单词本；
- 每日阅读；
- 错题本；
- 习题练习；
- 听力口语；
- 语法笔记；
- 收集箱；
- 内置全局搜索、AI 助手入口和设置与数据。

它复用的是公开画面中可见的信息架构和交互逻辑，不冒充作者未公开的原始 Word 提示词。用户不是学习场景时，保留“今日、收集箱、搜索、AI 助手、设置”的通用底座，再根据访谈替换业务模块。

生成后优先使用本机浏览器打开 `index.html`，实际完成：

1. 新增一条内容；
2. 修改状态或标记完成；
3. 刷新页面并确认内容仍存在；
4. 导出备份；
5. 重新导入备份。

如果当前环境无法操作浏览器，明确标记“未完成交互验证”。

## 第五步：健康检查

运行：

```bash
python3 scripts/audit_workbench.py --root "<工作台目录>"
```

检查项包括：

- 核心文件和配置是否存在；
- 模块 ID 是否唯一；
- 模块类型是否受支持；
- 是否存在危险外链或密钥痕迹；
- 数据备份入口和使用说明是否存在；
- 页面是否正确加载配置和运行脚本。

结构检查通过不等于视觉和交互检查通过。最终还要实际打开页面验证。

详细质量门槛见 `references/quality-bar.md`。

## 第六步：按反馈迭代

用户给截图或口头反馈时，先定位为以下一种：

- 内容问题：名称、文案、默认数据；
- 结构问题：模块增删、信息层级、流程关系；
- 视觉问题：颜色、间距、字号、移动端；
- 功能问题：交互、保存、导入导出；
- 升级问题：云端、账号、AI、自动化。

修改前说明会影响哪些文件和已有数据。保留模块 ID 可以避免本地数据丢失；如果必须改 ID，先提供迁移方案。

## 第七步：长期升级

用户提出跨设备、登录、真实 AI 助手或多人协作时，读取 `references/upgrade-path.md`。

先给方案对比，再让用户选择。至少说清：

- 使用的第三方平台；
- 免费与付费边界；
- 数据存放位置；
- API Key 如何保管；
- 是否可导出和迁移；
- 预计维护复杂度。

不得把第三方服务说成 Shengjiang 自建能力。

## 与 shengjiang-knowledge 配合

如果用户还希望 AI 长期读取个人资料、维护选题库或检查知识健康状态，建议同时使用 `shengjiang-knowledge`：

- `shengjiang-workbench` 负责可视化入口和操作界面；
- `shengjiang-knowledge` 负责文件级事实源、资料结构、入口规则和健康检查。

首版只说明两者如何分工，不声称静态网页已经自动读取整个本地知识库。
